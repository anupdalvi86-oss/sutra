# Sutra operating model

Supabase stores the role registry, assigned work, approvals, budgets and audit trail. The role permissions and `can_delegate_to` arrays are catalog metadata; they do not grant a process direct database, GitHub, shell, payment or messaging authority. Runtime handoffs are created by the fixed, database-backed workflows below. Every operation still passes through the service boundary and its authorization RPCs.

## Role contracts

| Role | Responsibilities | Catalog permissions | Catalog delegation targets | Inputs and persisted outputs |
|---|---|---|---|---|
| CEO | Translate founder objectives into accountable plans; coordinate and report | Read company state; create project proposal; delegate work (workflow metadata only) | CPO, CTO, CFO, COO, CMO, Sales, Governance/Audit | Founder request, company state and reviewed department artifacts → bounded decision review (`summary`, `recommendation`, `evidence`, `assumptions`, `risks`, `milestones`, `acceptance_criteria`) |
| CTO | Technical direction; engineering sequence | Read company state; create engineering tasks; request technical approval | Architect, Developer, QA, Security, DevOps | Approved/reviewed proposal and technical risks → bounded decision review; approved engineering work → task assignments and acceptance criteria through the workflow |
| CPO | Customer/problem research; product scope | Read product state; create product artifacts | Product Manager, Sales, CMO | Founder proposal → cited decision review; approved research task → private `market_research` artifact with customer segments, competitor evidence, buyer workflows, market gaps and pricing signals |
| CFO | Evaluate budgets and financial controls | Read financial state; request budget approval | Governance/Audit | Requested budget, active database policies and matching budgets → `decision` plus rationale; this role decision is not spend authorization |
| COO | Operational readiness and incident response | Read company state; create operations tasks | DevOps, Governance/Audit | Approved task and service context → `operations_plan` with `operational_dependencies`, `readiness_checklist`, `incident_plan` |
| Product Manager | Roadmap, requirements, acceptance outcomes | Read product state; create product artifacts | Architect, Developer, QA | Approved project and prior reviews → `product_plan` with `scope`, `milestones`, `acceptance_criteria`; this plan gates founder approval and engineering task creation |
| Architect | Technical design and interfaces | Read engineering state; create design artifacts | Developer, Security, DevOps | Approved assigned task and acceptance criteria → `technical_design` with `design`, `components`, `security_risks` |
| Developer | Implement approved work in GitHub branch/PR | Read assigned tasks; propose code changes | None | Founder-authorized, dispatched task → branch, GitHub PR and CI evidence; task completion follows merge and successful CI on the same SHA |
| QA | Acceptance verification | Read review tasks; record test results | None | Open PR with successful CI, verified SHA and acceptance criteria → named reproducible test evidence; a pass needs direct GitHub evidence |
| Security | Threat, dependency and release review | Read security scope; record reviews | None | QA-passed review and same verified SHA → bounded security checks, findings with severity/owner/remediation and explicit release blockers |
| DevOps | Deployment configuration, observability and recovery | Read deployment state; propose deployment changes | None | Approved assigned work → `release_plan` with `deployment_steps`, `health_checks`, `rollback_steps`; proposal alone cannot deploy |
| CMO / Marketing | Positioning and campaign proposals | Read marketing state; draft campaigns | Product Manager, Sales | Approved project/task context → internal `campaign_draft` (`audience`, `positioning`, `draft_copy`, `claims`, `success_metrics`). A separate customer-email action must pass consent, active-task, legal-hold and shared-budget checks before it can enter the private outbox. |
| Sales | Qualification and sales artifacts | Read sales state; draft lead artifacts | Product Manager, CMO | Approved project/task context → internal `sales_handoff` (`ideal_customer_profile`, `lead_criteria`, `qualification_questions`, `first_contact_draft`). A separate customer-email action must pass consent, active-task, legal-hold and shared-budget checks before it can enter the private outbox. |
| Governance / Audit | Independent controls assessment | Read audit state; record findings | None | Assigned control scope and evidence → `governance_review` with `controls_checked`, `findings`, `recommendation`; cannot change policy or approve spend |

Catalog permissions describe intended capabilities, not a tool allowlist. Persisted effects are limited to workflow RPCs: proposal/review artifacts, assigned tasks, metered runs, audited decisions and evidence. Codex can open a PR but cannot merge or deploy. The separate release worker can merge only under the database-gated founder grant after same-SHA CI, QA and Security pass; it cannot change spending authority. The private customer-email outbox now has an opt-in Resend delivery worker, disabled by default. Each message requires a recorded purpose-specific consent, a current non-unsubscribed address, the exact active Sales/Marketing task assignment, an active initiative assessed within budget, no project legal hold/open legal escalation, and a fresh reservation through the shared all-in spend policy. A database insert guard independently requires an active initiative, a `within_cap` assessment, a `proceed_within_cap` recommendation, and a numeric CFO estimate within the requested budget before an email action can persist; a failed insert rolls back its attempted reservation. Authorization is checked again before the provider request. Only one request is attempted: an expired lease, timeout, conflict, malformed response or other ambiguous outcome becomes terminal `unknown`; the complete spend reservation remains held. Confirmed delivery also keeps its reservation unknown until provider billing is reconciled. Audit records omit recipient and body. The role-agent workflow is not yet wired to enqueue messages. Activation requires `SUTRA_ENABLE_CUSTOMER_EMAIL_WORKER=true`, `SUTRA_CUSTOMER_EMAIL_SEND_MODE=live`, `RESEND_API_KEY`, a verified `SUTRA_CUSTOMER_EMAIL_FROM`, and a database-backed per-message cost ceiling plus provider billing reconciliation. Live customer sending is not enabled as part of this implementation. The founder can use `CEO, set legal hold <project-id> because <reason>.` and `CEO, clear legal hold <project-id> because <reason>.`; both changes are audited, and clearing a hold does not resume a paused initiative or close an open legal case.

## All-in initiative budget flow

Production initiative intake requires an explicit EUR ceiling before paid work. The CFO records an all-in estimate by cost category; when that estimate fits the cap and CFO/PM reviews succeed, the project activates without a second routine founder approval. A higher estimate pauses work with the gap; a legal issue or do-not-proceed recommendation pauses the initiative. The founder can change the ceiling only through the audited Telegram command `Increase initiative budget <project-id> to €<amount> because <reason>.` That command does not initiate a retry or decide a legal issue.

Project expenses and model reservations are represented in `initiative_budget_ledger`; unresolved usage stays reserved. Every project cost is checked against the remaining all-in cap and matching configured transaction, daily, monthly, company, project, department, agent, category and vendor limits. A cost inside the reviewed initiative ceiling does not create a new routine approval request. Sales and Marketing outputs remain private drafts. Zendesk intake stores signed ticket state metadata only; a service-role-only aggregate RPC gives CEO, COO and Sales reports queue counts by status, open priority and open-case age without exposing ticket IDs or message content. Age buckets are workload indicators, not promised response-time SLAs. This is not yet an agent triage workflow. HubSpot contact upserts now use a budget-reserved, consent-gated outbox and leased worker, disabled by default. Provider plan fees require separate initiative cost authorization. CRM consent is founder-recorded with evidence in Telegram; withdrawal cancels queued exports. Customer message retention, support ticket triage and provider replies remain future work and must be wired through assigned, spend-gated tasks and legal escalation checks.

## Handoff sequence

1. Founder-only Telegram identity submits a bounded proposal.
2. Durable reviews run CEO → CPO (research) → CTO → CFO → Product Manager. A failed/invalid artifact blocks the next stage; retries are bounded and metered. The CFO adds a category-by-category estimate and the PM review is the final routine review.
3. The database activates an initiative after CFO and PM reviews when the all-in estimate fits the founder's stated cap. A budget gap or legal issue pauses for the founder. The approved cap never authorizes spend above the central ledger and budget controls.
4. Approved engineering tasks flow through Architect/Developer. A successful CI run on an open PR releases QA; passing QA releases Security. Only same-SHA CI plus passing QA and Security evidence can authorize the separate merge worker. A changed PR head resets the review tasks and makes old evidence ineligible. Developer completion still requires the merged PR and CI result for the same SHA. The founder can defer reviews through audited commands, but deferred or missing evidence prevents an automatic merge.
5. CPO research, product/operations/release/campaign/sales/governance task artifacts are available only for approved, assigned tasks and are stored as private artifacts. CPO factual claims require cited HTTPS evidence. Marketing and sales handoffs remain internal drafts. The internal email-action endpoint can persist an opted-in, budget-reserved send request, and the opt-in provider worker can deliver it after runtime configuration. Ambiguous sends are terminal and retain unknown reservations; no live provider is configured by default.

The production proposal review ordering is CEO → (CPO research and CTO feasibility at the same stage) → CFO → PM. It supports two service-role-only database lease slots and defaults to one worker. Configure two only when the inference provider supports that concurrency. Model-spend reservations remain serialized against the EUR ledger, and each run retains its normal approval and hard-stop checks.

The metadata graph is checked by `supabase/tests/agent_delegation_test.sql`; `can_delegate_to` is not a generic runtime delegation API. The actual workflow transitions are server-owned and database-gated, which prevents an agent from self-assigning work or widening its authority by editing role metadata.

Review deferrals are founder controls, not agent task updates. The database verifies the configured founder identity, approved project, QA/Security assignments, exact direct-child roles and valid workflow states in one transaction. It writes one founder audit event per deferred review and a system event for the internal child release. Agents cannot set `deferred`, and the task evidence gate still rejects review completion without persisted passing evidence bound to the verified Developer commit.

The founder may use `retry agent review <run-id>` to recover a terminal, recognized failure in CEO/CPO/CTO/CFO when all earlier stages succeeded. This requeues the same run within its existing three-attempt ceiling, preserves every prior reservation (including unknown usage), and writes an audit event. It cannot retry nonterminal runs or failures outside the recognized recoverable set. The separate `retry PM task <task-id>` command recovers a blocked Product Manager planning task only when its project has recorded founder approval, the failed artifact has a recognized validation error, and fewer than three task-artifact runs exist. It changes no project or expense approval, retains unknown reservations, and writes a founder audit event; any new model call still needs normal spend preflight and budget capacity. The `retry CPO research <task-id>` command is limited to the same blocked CPO research task after its terminal malformed-response failure, with a founder-approved project and a held unknown reservation. It uses the configured OpenAI GPT-6 Luna route, preserves every prior reservation, and allows at most three total artifact runs and one queued retry request at a time. The database audits the request; fresh inference remains subject to normal spend preflight and monthly hard stop. No project spending or release authority is granted.

For the pre-approval Product Manager stage, `retry PM review <run-id>` normally stays within three attempts. If all three end in a terminal invalid-artifact-schema failure with reconciled usage, only the founder can request one final recovery attempt. This remains the same PM run after CEO, Product, CTO, and CFO succeeded and while the project budget approval is pending. Unknown reservations are preserved, the worker must obtain a new reservation under the existing spending policy and monthly hard stop, and a fourth failure is terminal. The request is audit logged and grants no project spending authority.

For the specific Sales handoff, `retry Sales task <task-id> after artifact schema fix` is a one-time founder-only recovery after three terminal `invalid_artifact_schema` attempts and only when all three prior reservations are reconciled. It requeues the same task in the same founder-approved project, does not create a run or spend reservation at command time, and records an audit event. The next execution keeps the standard three-attempt ceiling and still needs a fresh normal spend reservation within policy and the monthly hard cap. This command adds no project-spend, merge, or release authority.
