Hermes keeps its provider credentials separately. Never paste replacement secrets into Telegram, GitHub, logs, prompts, or this repository.

The Zendesk support-inbox stage is opt-in and should remain disabled until the support retention and task-routing policy is ready. Apply the `zendesk_support_inbox` migration first. Configure `ZENDESK_WEBHOOK_SECRET` privately and set `SUTRA_ENABLE_ZENDESK_WEBHOOK=true` only when a Zendesk trigger is ready. Point it to `POST /webhooks/zendesk` and include exactly these JSON fields: `id` (ticket numeric ID), `status` (`new`, `open`, `pending`, `hold`, `solved` or `closed`), `priority` (`null`, `low`, `normal`, `high` or `urgent`) and `updated_at` (timezone-aware ISO-8601 timestamp). Zendesk's standard signature headers must reach Sutra unchanged: `X-Zendesk-Webhook-Timestamp` and `X-Zendesk-Webhook-Signature`. Sutra verifies the signature over timestamp plus raw request bytes and rejects timestamps outside five minutes. Do not include ticket body, requester email, attachments or extra fields; the endpoint rejects extra JSON fields and the database deliberately stores no message content. Health reports whether the endpoint is configured; it is not a requirement for readiness while disabled. No live provider call is needed to test this code.

Assigned Sales tasks may read Zendesk content ephemerally to prepare a support triage and private reply draft. Apply `20260930035312_zendesk_task_scoped_context.sql`, configure `ZENDESK_SUBDOMAIN`, `ZENDESK_AGENT_EMAIL`, and a narrowly scoped private `ZENDESK_API_TOKEN`, then set `SUTRA_ENABLE_ZENDESK_SUPPORT_CONTEXT=true`. The database authorizes the exact in-progress Sales task only when its text names one `Zendesk ticket ID: <id>`, the case is open, and its initiative is active, assessed within budget, and free of legal holds/escalations. Sutra fetches the ticket and at most five recent public comments in memory; raw ticket text and comments are not persisted. The Sales artifact retains only a bounded category, urgency, and unsent reply draft. No Zendesk reply is sent by this stage. Keep it disabled until the support initiative's all-in budget and Zendesk privacy/retention terms are recorded.

## Hermes and worker safety

Hermes uses a pinned upstream image and the persistent volume at `/opt/data`. Sutra's startup constrains the API toolset to `web`; it does not expose terminal, process, or file-write tools. Do not expand that toolset without a sandboxed backend. The private API always requires an API key. Model execution is locked to an active database price profile and bounded token/iteration limits. The worker reserves the profile maximum before provider calls and reconciles observed usage afterward. Approval-pending work makes no provider call. Unknown or out-of-profile usage fails closed and retains the full reservation. Missing or malformed usage emits only an allowlisted provider/model label and token-field shape; token counts and raw provider response content are not logged.

Production supports two bounded database lease slots and defaults to one isolated worker thread; `SUTRA_AGENT_WORKER_CONCURRENCY` accepts only `1` or `2`. Keep it at `1` with the currently observed OpenAI concurrency limit. Lease slots expire after ten minutes after a process crash. CPO research and CTO feasibility can run concurrently at proposal stage 2, subject to provider capacity. Spend reservations stay serialized by the database EUR ledger lock. The lease slots do not grant approval or spending authority.

The code-release worker logs a fixed stage (`github_evidence_poll`, `database_claim`, `database_authorization`, `github_pull_request_read`, `github_merge`, `database_merge_reconciliation`, or `database_result`) plus an allowlisted error category. It does not log upstream response bodies, request URLs, or headers. Consecutive integration failures back off from the configured idle interval with exponential delay, capped at five minutes; an idle or successful cycle resets the delay. Use the stage and sanitized category to target a failing dependency without enabling verbose request logging.

Only an assigned task in an approved project can write a role artifact. The founder's standing repository authorization permits scoped code tasks, branches, PRs, QA, Security, merges, and deployment; it does not grant spending authority. The database audits that grant and gates GitHub dispatch/Codex to its exact approved task scope. The release-gate stage in this sprint adds pre-merge QA and Security evidence for the exact open PR head: successful CI releases QA; passing QA releases Security; the separate merge worker rechecks the live grant, project/task scope, CI, both reviews, and expected PR head immediately before a squash merge to `main`. A PR head change invalidates stale reviews and requires them to run again. The release worker is opt-in with `SUTRA_ENABLE_CODE_RELEASE_WORKER=true` and has no model-provider access. Marketing and Sales artifacts remain internal drafts. This sprint includes opt-in Resend email delivery and HubSpot contact synchronization; both remain disabled unless the required credentials, consent, and assessed initiative budgets are present. No customer email or CRM provider call has been made.

Do not enable the worker until the migration is applied, a specific initiative has a founder-approved all-in budget and CFO assessment, the HubSpot plan cost has been reserved separately, and the customer has documented CRM sharing consent. The internal enqueue endpoint is `POST /internal/customer-crm-sync`; it requires the existing `SUTRA_INTERNAL_API_TOKEN`, a task assigned to the active Sales agent, an active assessed project, a positive EUR reservation estimate, and an idempotency key. The database checks budget, consent, unsubscribe status, legal holds/escalations, task assignment and remaining funds, then holds the reservation before the provider call. The dispatcher creates/reuses a GitHub issue for an approved Developer task and audits the handoff. The metered Codex runner verifies signed issue content, obtains a one-time database claim and can push a task branch/open a PR; it cannot merge or deploy. For every run it writes a private `$CODEX_HOME/config.toml` that selects the custom `sutra_metered` Responses provider and the loopback proxy URL. `OPENAI_BASE_URL` alone is not sufficient to route Codex CLI traffic. The child receives only a dummy `OPENAI_API_KEY`; its model requests must reach the metering proxy, which applies the live database price profile and request authorization before forwarding them with the server-held key. WebSocket and automatic request retries are disabled so each admitted request is explicitly metered. PR/CI evidence must match the same SHA before Developer completion. With the release worker enabled, QA and Security review the current open PR before merge, and only the independent gated worker can squash-merge the exact authorized head. The webhook endpoint is `POST /webhooks/github`; it validates the SHA-256 signature and repository. Railway's API can remain private when its server-side GitHub poller is used.

Railway API logs provide bounded Codex runner diagnostics (`codex_issue_rejected`, `codex_task_authorization_not_ready`, `codex_task_claim_rejected`, and `codex_runner_cycle_failed`). Exception text, issue bodies, credentials, and model prompts are excluded. Set `SUTRA_LOG_LEVEL` to adjust process log verbosity; the default is `INFO`.

The required CI workflow runs Python tests/Bandit, migrations/pgTAP/database lint, container checks, and secret scanning. The exact-head release gate is active in production. See [STATUS.md](../STATUS.md) for the latest verified state and outstanding integration gaps.

## Telegram

Founder interface: [@sutra86bot](https://t.me/sutra86bot). Production startup validates the bot identity and the registered founder ID. The bot only accepts one-to-one messages from the configured founder. The approval list and status reads are audit logged; approval/rejection actions are founder-only audited operations. The bot supports status, proposal intake, approval listing/decisions, and bounded recovery commands.

Use `CEO, give me company status.` for a board-style company report. Other roles accept `ROLE, give me department status.`. Reports include objectives, project owners, open task queues, recent completions, blockers, pending approvals, and financial controls. Company, Marketing, and Sales reports also show campaign/customer pipeline details and explicitly say when those pipelines have no records; customer email fields are not fetched for these reports. The consolidated sprint adds an aggregate-only support queue summary to CEO, COO and Sales reports; its service-role RPC returns counts only, not ticket IDs or message content. `CEO, show my approvals.` lists founder decisions ready or pending. `retry GitHub dispatch <task-id>` requeues only an exhausted permission-denied dispatch for the same founder-approved Developer task, with a three-cycle lifetime bound and an audit record. `CEO, show Codex no-request retry limit.` reads the database setting. `CEO, set Codex no-request retry limit to 3 total attempts.` changes it through a founder-only, audit-logged RPC and does not trigger a retry. The production setting and hard maximum are three total attempts per execution; the founder may lower it to one or two. `retry Codex task <task-id>` runs only when database checks confirm the same approved Developer task and scope, a terminal prior attempt with zero provider requests/tokens, and remaining configured capacity. It preserves the old unknown reservation and creates a fresh reservation through the existing spend policy and monthly hard cap. `retry Sales task <task-id> after artifact schema fix` is a founder-only, one-time recovery for a blocked approved Sales artifact after three schema-validation failures and reconciled reservations. It requeues the same task but does not create a run or spend reservation; the new execution remains subject to normal spend controls. Campaign and sales drafting is internal only. Rotate credentials previously shared in chat after validation and replace them directly in their private Railway variables.

## Local development and verification

Python 3.12+:

```sh
python3 -m unittest discover -s tests -v
python3 -m compileall -q sutra tests
python3 -m bandit -q -r sutra -ll
```

With Docker and Supabase CLI, discover command options using `supabase --help`, then run local migrations, `supabase test db`, and database lint. CI runs the hosted migration/pgTAP/lint workflow. For the API, copy `.env.example` to `.env`, add only local server-side values, then run `SUTRA_BIND_HOST=127.0.0.1 python3 -m sutra.server`. `.env` is ignored by Git. Never commit credentials or tokens.
