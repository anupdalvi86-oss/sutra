# Deployment and operations

| Service | Runtime | Persistent state | Secrets/config |

| `sutra-api` | Python API/Telegram/worker on port 8080, built from `sutra/Dockerfile` | None | Supabase service-role, Telegram bot + founder ID, independent internal/Hermes credentials, GitHub token + webhook secret, worker configuration |

Both services are Online. The latest verified production rollout includes merged PRs #209, #210, and #211; after #211, Railway reported API and Hermes Online, `/health` returned 200, and the founder Telegram command for standing code authority worked. The Hermes service uses its persistent volume at `/opt/data`. Railway watch paths scope API deployments to `/sutra/**` and `/railway.api.json`, and Hermes deployments to `/Dockerfile`, `/hermes/**`, and `/railway.json`. Documentation, CI, and database-only commits skip runtime rebuilds. The API liveness probe is `/health`; `/ready` additionally checks Supabase and every enabled integration. When the agent worker is enabled, `/ready` requires both a running worker and a healthy private Hermes health endpoint. The API and Hermes endpoints are private; no public API URL is configured. Hermes has restart-on-failure and the mounted volume. Keep the Supabase service-role credential only on `sutra-api`.

Railway variables must be set in the service environment, not committed. API integration variables include `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_FOUNDER_USER_ID`, `SUTRA_INTERNAL_TOKEN`, `HERMES_AGENT_API_URL`, `HERMES_AGENT_API_KEY`, `HERMES_HEALTH_URL` (private Hermes `/health` URL), `SUTRA_HERMES_PROVIDER`, `SUTRA_HERMES_MODEL`, optional `SUTRA_HERMES_ROLE_ROUTES`, `GITHUB_TOKEN`, `GITHUB_WEBHOOK_SECRET`, `GITHUB_REPOSITORY`, and opt-in dispatcher/Codex settings. Hermes keeps its provider credentials separately. Never paste replacement secrets into Telegram, GitHub, logs, prompts, or this repository.

## Hermes and worker safety

Hermes uses a pinned upstream image and the persistent volume at `/opt/data`. Sutra's startup constrains the API toolset to `web`; it does not expose terminal, process, or file-write tools. Do not expand that toolset without a sandboxed backend. The private API always requires an API key. Model execution is locked to an active database price profile and bounded token/iteration limits. The worker reserves the profile maximum before provider calls and reconciles observed usage afterward. Approval-pending work makes no provider call. Unknown or out-of-profile usage fails closed and retains the full reservation. Missing or malformed usage emits only an allowlisted provider/model label and token-field shape; token counts and raw provider response content are not logged.

Production currently uses one service-role-only Supabase execution lease before claiming any proposal, review or task-artifact work. The `feat/parallel-agent-reviews` branch changes this to two bounded database lease slots and defaults to one isolated worker thread; `SUTRA_AGENT_WORKER_CONCURRENCY` accepts only `1` or `2`. Keep it at `1` with the currently observed OpenAI concurrency limit. Lease slots expire after ten minutes after a process crash. The branch also makes CPO research and CTO feasibility ready concurrently at proposal stage 2, subject to provider capacity. Spend reservations stay serialized by the database EUR ledger lock. These changes are not in production until the migration and API branch are reviewed and deployed. The lease slots do not grant approval or spending authority.

Only an assigned task in an approved project can write a role artifact. The founder's standing repository authorization permits scoped code tasks, branches, PRs, QA, Security, merges, and deployment; it does not grant spending authority. The database audits that grant and gates GitHub dispatch/Codex to its exact approved task scope. The release-gate stage in this sprint adds pre-merge QA and Security evidence for the exact open PR head: successful CI releases QA; passing QA releases Security; the separate merge worker rechecks the live grant, project/task scope, CI, both reviews, and expected PR head immediately before a squash merge to `main`. A PR head change invalidates stale reviews and requires them to run again. The release worker is opt-in with `SUTRA_ENABLE_CODE_RELEASE_WORKER=true` and has no model-provider access. Marketing and Sales artifacts remain internal drafts. CRM, customer support, and email providers are not integrated, and no customer messages have been sent.

## GitHub and Codex

The repository is public, so an anonymous repository GET alone does not prove token identity. The latest verified GitHub settings page has only Sutra selected, with Metadata read, Issues read/write, Contents read/write, Pull Requests read/write and Actions read; the token has no repository Administration permission. [PR #160](https://github.com/anupdalvi86-oss/sutra/pull/160) is merged. Supabase records its successful run `36541235879` with CI head SHA `5c7977fc9cb81845231392ae96c37d6fd6efc2ea`, exactly matching the merged PR head. The production dispatch row records `pull_request_merged=true`. PR #166 supplies the workflow-run-ID, URL and exact-head checks. The PR #160 draft migrations remain local-only and are not in the production migration history.

The dispatcher creates/reuses a GitHub issue for an approved Developer task and audits the handoff. The metered Codex runner verifies signed issue content, obtains a one-time database claim and can push a task branch/open a PR; it cannot merge or deploy. For every run it writes a private `$CODEX_HOME/config.toml` that selects the custom `sutra_metered` Responses provider and the loopback proxy URL. `OPENAI_BASE_URL` alone is not sufficient to route Codex CLI traffic. The child receives only a dummy `OPENAI_API_KEY`; its model requests must reach the metering proxy, which applies the live database price profile and request authorization before forwarding them with the server-held key. WebSocket and automatic request retries are disabled so each admitted request is explicitly metered. PR/CI evidence must match the same SHA before Developer completion. With the release worker enabled, QA and Security review the current open PR before merge, and only the independent gated worker can squash-merge the exact authorized head. The webhook endpoint is `POST /webhooks/github`; it validates the SHA-256 signature and repository. Railway's API can remain private when its server-side GitHub poller is used.

Railway API logs provide bounded Codex runner diagnostics (`codex_issue_rejected`, `codex_task_authorization_not_ready`, `codex_task_claim_rejected`, and `codex_runner_cycle_failed`). Exception text, issue bodies, credentials, and model prompts are excluded. Set `SUTRA_LOG_LEVEL` to adjust process log verbosity; the default is `INFO`.

The required CI workflow runs Python tests/Bandit, migrations/pgTAP/database lint, container checks, and secret scanning. This release-gate change is not active in production until the PR's checks pass, its migration is applied, and Railway deploys the API. ## Telegram

Founder interface: [@sutra86bot](https://t.me/sutra86bot). Production startup validates the bot identity and the registered founder ID. The bot only accepts one-to-one messages from the configured founder. The approval list and status reads are audit logged; approval/rejection actions are founder-only audited operations. The bot supports status, proposal intake, approval listing/decisions, and bounded recovery commands.

Use `CEO, give me company status.` for a board-style company report. Other roles accept `ROLE, give me department status.`. Reports include objectives, project owners, open task queues, recent completions, blockers, pending approvals, and financial controls. Company, Marketing, and Sales reports also show campaign/customer pipeline details and explicitly say when those pipelines have no records; customer email fields are not fetched for these reports. `CEO, show my approvals.` lists founder decisions ready or pending. `retry GitHub dispatch <task-id>` requeues only an exhausted permission-denied dispatch for the same founder-approved Developer task, with a three-cycle lifetime bound and an audit record. `CEO, show Codex no-request retry limit.` reads the database setting. `CEO, set Codex no-request retry limit to 3 total attempts.` changes it through a founder-only, audit-logged RPC and does not trigger a retry. The production setting and hard maximum are three total attempts per execution; the founder may lower it to one or two. `retry Codex task <task-id>` runs only when database checks confirm the same approved Developer task and scope, a terminal prior attempt with zero provider requests/tokens, and remaining configured capacity. It preserves the old unknown reservation and creates a fresh reservation through the existing spend policy and monthly hard cap. `retry Sales task <task-id> after artifact schema fix` is a founder-only, one-time recovery for a blocked approved Sales artifact after three schema-validation failures and reconciled reservations. It requeues the same task but does not create a run or spend reservation; the new execution remains subject to normal spend controls. Campaign and sales drafting is internal only. Rotate credentials previously shared in chat after validation and replace them directly in their private Railway variables.

## Local development and verification

Python 3.12+:

```sh
python3 -m unittest discover -s tests -v
python3 -m compileall -q sutra tests
python3 -m bandit -q -r sutra -ll
```

With Docker and Supabase CLI, discover command options using `supabase --help`, then run local migrations, `supabase test db`, and database lint. CI runs the hosted migration/pgTAP/lint workflow. For the API, copy `.env.example` to `.env`, add only local server-side values, then run `SUTRA_BIND_HOST=127.0.0.1 python3 -m sutra.server`. `.env` is ignored by Git. Never commit credentials or tokens.
