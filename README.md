# Sutra

Sutra is a governed company operations runtime. Supabase holds authoritative company state and database-enforced approval policy; GitHub holds software artifacts; Hermes is the agent runtime; Telegram is the founder interface.

## Current implementation

- The Supabase migrations define all 14 organizational roles and the operational schema, enable RLS, withhold direct access from `anon` and `authenticated`, and limit service-role writes to audited database functions for financial and governance tables.
- Spending policies and budget limits live in Supabase. Defaults are `<= €10` automatic, `> €10 to €50` department head, `> €50 to < €200` CFO and CEO, and `>= €200` founder. All boundaries are configurable through founder-verified functions. Company, project, department, agent, category, vendor, transaction, daily, monthly and lifetime budgets support warnings and hard stops. Current live limits include the €8 monthly AI-inference hard stop and €500 project ceilings; no overall company operating budget is set. See [STATUS.md](STATUS.md) for the latest project and approval inventory.
- Department-head approvals are disabled until the founder assigns an active agent to each department through the audited `sutra_set_company_setting` RPC (`department_head:<department UUID>` → agent UUID). A founder may assign a leader from another department for small departments; the assignment is scoped to the named department. Agents cannot approve their own expenses.
- Production initiative intake requires an explicit all-in ceiling and CFO estimate; a within-cap proposal proceeds through the PM review without a second routine founder approval. The founder-only audited review-deferral command can defer QA and Security while clearly leaving both reviews incomplete; it releases only the directly dependent internal DevOps planning task and grants no spending, merge or release authority. QA and Security evidence gates remain in place for completion/release. After approval, the leased Hermes worker writes role-specific, private task artifacts for PM, Architect, COO, DevOps, CMO, Sales and Governance/Audit. It settles model usage against the database reservation before artifact persistence; exact task acceptance criteria and role contracts are checked by the database. Marketing/Sales deliverables are internal drafts only.
- The private Python service exposes health and token-protected internal spend, role-approval and task-update endpoints. Telegram polling is restricted to the configured founder in a private chat. CEO and department briefs report projects/objectives, open tasks, recent completions, blockers, pending approvals, budgets and relevant customer/marketing pipelines; engineering delivery health comes from a bounded service-role-only RPC. Failure categories are allowlisted and raw provider responses are not included. Supabase, Telegram and internal API credentials are stored on the private API service; Hermes model credentials stay on the separate Hermes service.
- The maximum total attempts for a Codex execution after verified no-request failures is a founder-adjustable, audited Supabase setting (default 3, hard maximum 3; founder may lower it to 1 or 2). Telegram commands are `CEO, show Codex no-request retry limit.` and `CEO, set Codex no-request retry limit to 3 total attempts.` Changing the setting only changes the limit; it never starts a retry. Every retry still requires the same founder-approved Developer task and scope, a terminal prior attempt with zero provider requests/tokens, preservation of the unknown reservation, and a fresh reservation through existing spend policies and the monthly hard cap. It adds no project-spend, merge, or release authority.
- Kimi remains disabled for ordinary role work. The founder-only Telegram command `CEO, run one bounded Kimi usage probe.` queues one audited operational project with a fixed €0.10 project cap. The worker pins that single run to `kimi-coding:kimi-k2.6`, reserves through the active database price profile and ordinary spend policy, limits its response to 64 output tokens, and never retries it. Missing or malformed usage remains unknown and held; the command does not enable a Kimi role route.
- Unit tests cover command routing, founder identity checks, malformed requests and the central authorization endpoint. PostgreSQL policy tests cover spending boundaries, project approvals, budget stops, RLS, role approvals, per-run model spend reservations and audit writes.

The SQL workflow stores real work items and approval evidence. It does not fabricate research results. The GitHub dispatcher and metered Codex runner are gated by founder-approved Developer scope. A separate opt-in code-release worker can merge only a non-draft PR into `main` after successful CI, QA and Security evidence all match the current head SHA. Supabase checks the active founder repository grant immediately before the GitHub write, records each claim/result in the audit log, and never grants spending authority. New commits invalidate previous review evidence; GitHub also receives the expected head SHA on the merge request. The Codex runner itself still cannot merge or deploy. `SUTRA_ENABLE_CODE_RELEASE_WORKER` is off by default and uses the private API's existing narrowly scoped GitHub token; it makes no model calls. Repeated integration failures log only a fixed worker stage and safe error category, then back off to a five-minute maximum. See [deployment instructions](docs/DEPLOYMENT.md) and [STATUS.md](STATUS.md) for live state.

## Initiative budgets and operating autonomy

The all-in initiative budget workflow is active in production. Each initiative has an explicit EUR ceiling that covers model usage, development, tools, hosting, marketing, operations and contingency. The CFO records a costed estimate before paid work; a gap or legal question pauses the initiative. The configured founder can change a ceiling through the audited Telegram command `Increase initiative budget <project-id> to €<amount> because <reason>.` The shared ledger preserves actual, reserved and unknown costs and applies company, project, department, agent, category, vendor and time-period hard stops. Ordinary spending inside an approved, assessed initiative does not create another approval request.

The founder-only legal escalation inbox stores CFO and Sales/Marketing task legal cases in Supabase. A role task can flag a contract, legal interpretation, or binding commitment; the database records an audited case, pauses the initiative, blocks same-task outreach, and prevents new paid reservations. Telegram can list cases (`CEO, show legal escalations.`) and record a reasoned disposition (`record legal case <case-id> as seek legal counsel because <reason>.`). Allowed dispositions are limited to continue within the existing budget, stop the initiative, or seek counsel. Recording one is audited and does not unpause the project, authorize a contract or binding commitment, or increase the budget.

The customer-operations foundation adds a private `/internal/customer-email` enqueue endpoint and a service-only Supabase outbox. Assigned Sales and Marketing task artifacts can now request up to five messages, only for customer UUIDs explicitly present in that task. A database trigger sends each request through the same audited outbox and supplies the founder-configured per-message ceiling as its ledger reservation; the model cannot quote a lower cost. The queue requires a valid customer email plus recorded purpose-specific consent and no unsubscribe, an active assigned task, a CFO `within_cap` assessment with `proceed_within_cap`, no project legal hold/open legal escalation, and remaining all-in budget. Blocked actions are audit logged without recipient or message content, while the internal deliverable completes. A Resend delivery adapter and leased worker are available behind explicit configuration; they remain disabled in this environment. Read the ceiling with `CEO, show customer email cost ceiling.` or set it with `CEO, set customer email cost ceiling to €0.05 because <reason>.` The setter is founder-only, range-checked, blocks unsafe changes against queued/sending work and records old/new values and reason in the audit log; it never starts delivery. The worker rechecks consent, task assignment, legal state, budget and ceiling immediately before sending. It never retries ambiguous outcomes: timeouts, malformed responses, conflicts and expired leases become terminal `unknown` with the full reservation held. Confirmed sends also remain unknown in the shared ledger until provider billing is reconciled. Board status shows queue state without exposing addresses or message bodies. The founder may set or clear an audited project hold with `CEO, set legal hold <project-id> because <reason>.` / `CEO, clear legal hold <project-id> because <reason>.` No real messages were sent during this implementation. Live delivery still needs `SUTRA_ENABLE_CUSTOMER_EMAIL_WORKER=true`, `SUTRA_CUSTOMER_EMAIL_SEND_MODE=live`, a Resend API key, a verified sender address, a configured message ceiling, recorded customer consent, an initiative budget assessed within its cap, and provider billing reconciliation.

An inbound Zendesk stage adds `POST /webhooks/zendesk`, authenticated with Zendesk's timestamped HMAC signature and a five-minute replay window. It stores an idempotent, audited support-case state in Supabase and ignores older provider updates. The allowlisted record includes only ticket ID, status, priority and provider update time; free-form messages, requester details, attachments and raw webhook payloads are discarded. This endpoint is disabled by default. Activation requires `SUTRA_ENABLE_ZENDESK_WEBHOOK=true`, a private `ZENDESK_WEBHOOK_SECRET`, a Zendesk trigger that sends the exact four-field JSON schema documented in [deployment setup](docs/DEPLOYMENT.md), and the support-inbox migration. The consolidated sprint adds a service-role-only aggregate RPC for CEO, COO and Sales reports; it exposes counts by status, open priority, and open-ticket age buckets plus the oldest open-ticket age, never ticket IDs or customer content. Age is an operational indicator, not a service-level promise. Assigned Sales tasks can now read one explicitly named open ticket through an opt-in Zendesk API reader after a database authorization check confirms the exact task, active assessed budget, and legal state. Ticket text and up to five recent public comments remain in memory for the model request; the task artifact stores only a bounded category, urgency, and private unsent reply draft. A legal question creates the existing founder case and pauses the initiative. This does not send replies. The context reader requires `SUTRA_ENABLE_ZENDESK_SUPPORT_CONTEXT=true`, a Zendesk subdomain, agent email and private API token; automated webhook-to-task routing and outbound replies remain future work.

A HubSpot contact upsert integration targets the [2026-09 Contacts API release](https://developers.hubspot.com/changelog/fall-2026-spotlight), using the documented [batch upsert contract and contact-write scope](https://developers.hubspot.com/docs/api-reference/latest/crm/activities/tasks/batch/upsert-tasks). A task-assigned Sales action can enter a private Supabase outbox only when the initiative is assessed within cap, remaining all-in budget covers a positive cost reservation, the customer has recorded CRM sharing consent, and no legal hold/escalation is open. It sends only email, name and company, keyed by email, and never copies free-form notes. The worker revalidates authorization before calling HubSpot. Confirmed API actions settle known per-call cost; ambiguous outcomes remain unknown with their reservation held and are not retried. `CEO, record CRM consent for <customer-id> because <evidence source>.` and `CEO, withdraw CRM consent for <customer-id> because <reason>.` are founder-only and audit logged; withdrawal cancels queued actions without starting a sync. The `/internal/customer-crm-sync` endpoint and HubSpot worker are opt-in and remain disabled by default. Activation needs `SUTRA_ENABLE_HUBSPOT_SYNC_WORKER=true`, `HUBSPOT_PRIVATE_APP_TOKEN` with `crm.objects.contacts.write`, an applied migration, recorded customer evidence, and an initiative all-in budget. HubSpot plan/subscription charges must be authorized as initiative costs separately; no provider API call or customer message has been made during implementation.

When a Codex process or usage settlement ends in a terminal failure, the database marks its Developer task `blocked` and records that transition. The founder retry path can reopen only that same approved scope after a terminal zero-request, zero-token failure and a fresh spend-policy reservation. A blocked task waiting for spend approval stays blocked; the retry controls add no project-spend, merge, or release authority.

The leased proposal/review/task-artifact worker is deployed and enabled. Before each provider request the worker reserves the profile's maximum three-iteration cost, waits for approval if required, begins the reservation, passes Hermes a bounded output-token cap and exact route lock, and reconciles observed usage before success. Unknown or out-of-profile usage keeps the full reserve and fails the run. The live database has founder-audited OpenAI GPT-6 Luna and Kimi K2.6 price profiles and an €8 monthly AI inference hard stop. Production proposal reviews run CEO first, then CPO research and CTO feasibility in parallel, followed by CFO and PM. The database has two coordinated lease slots; API concurrency remains one because the OpenAI account currently allows one concurrent request. Each reservation still serializes against the EUR ledger and existing spend policies. Unknown usage remains reserved and is never estimated or released; see [STATUS.md](STATUS.md) for the latest state.

An approved Developer scope also has a local, draft-only manual test-plan prototype. It produces synthetic plans without model calls, browser execution, GitHub writes or releases. See the deployment docs for its development-only API and lifecycle limits.

PM review requests use provider JSON mode and a strict single-object contract for the product plan. The founder can request a bounded retry from Telegram only while the project budget request is pending; each attempt still passes the database spend reservation and monthly hard stop. Unknown earlier usage remains reserved.

## Local verification

Python 3.12+ has no third-party dependencies:

```sh
python3 -m unittest discover -s tests -v
```

CI also runs Bandit 1.9.4 at medium severity or higher. Outbound HTTP requests are restricted to HTTPS or Railway's private `.railway.internal` network; the API binds to the container interface for Railway's health probe while public networking remains disabled.

GitHub Actions skips Python, database and container jobs for README, `STATUS.md` and Markdown-only changes under `docs/`; secret scanning still runs. Any code, configuration or workflow change runs the full CI suite.

Install Docker and the Supabase CLI, then run:

```sh
supabase stop --workdir .
supabase start --exclude realtime,storage-api,imgproxy,mailpit,studio,postgres-meta,edge-runtime,logflare,vector,supavisor
supabase db reset
supabase test db
```

`supabase stop` preserves the local database backup volume. The reduced service set starts the database, Auth, REST, and API gateway used by tests without optional analytics/vector services that may fail local health checks.

For the API, copy `.env.example` to `.env`, fill only the server-side integration values, then run `python3 -m sutra.server`. Never commit `.env` or place a Supabase service-role key in Hermes, a Telegram message, GitHub, or an agent prompt.

The local draft prototype exposes `POST /v1/drafts`, `GET /v1/drafts/{draft-id}`, `PATCH /v1/drafts/{draft-id}/review`, and owner-only `DELETE /v1/drafts/{draft-id}`. It is off by default and requires `SUTRA_ENV=development`, `SUTRA_ENABLE_DRAFT_API=true`, `SUPABASE_URL`, and `SUPABASE_ANON_KEY`; each request must carry a signed-in Supabase user's access token as `Authorization: Bearer <user-jwt>`. The API routes enable only when `SUTRA_ENV=development`, `SUTRA_ENABLE_DRAFT_API=true`, and the Supabase URL is local loopback; a hosted/production Supabase URL cannot activate this prototype. Local HTTP redirects cannot leave loopback. Do not enable this prototype in production. Run the Supabase commands above, then `python3 scripts/draft_auth_e2e.py` for a live local Auth/PostgREST check. It refuses non-loopback URLs, gives the Sutra API only the publishable/anon key, checks two-user isolation, draft deletion and append-only reviews, and removes its temporary Auth users. CI runs this integration against a disposable local Supabase stack.

## Railway services

The production Railway project uses two private services connected to this repository:

1. **Hermes** (`sutra`) builds from the repository root `Dockerfile` and starts the pinned, patched Hermes gateway. A Railway volume is mounted at `/opt/data` for persistent runtime state. Keep its model-provider credentials here, separate from Supabase credentials.
2. **Sutra API** (`sutra-api`) builds from root directory `/sutra` and `sutra/Dockerfile`, runs `python -m sutra.server` and listens on port 8080. It has `/health` configured as its Railway health check and is not publicly exposed. The Supabase service-role key, Telegram bot token, internal token and Hermes private API credentials are configured as Railway service variables; the founder ID is configured in both the API environment and Supabase. The proposal/task-artifact worker is enabled and uses database-approved model profiles and per-role routes.

`GET /health` reports process and integration status. `GET /ready` reports database readiness and checks each enabled integration, returning HTTP 503 with named blockers until usable. When the agent worker is enabled, readiness also requires a successful probe of the configured private `HERMES_HEALTH_URL`; a running Sutra worker alone is not sufficient. The probe accepts HTTPS or Railway's private `.railway.internal` HTTP network and never returns credentials. See [STATUS.md](STATUS.md) for current live verification and blockers.

## Founder commands

- `CEO, give me company status.`
- `CFO, give me department status.` (also CTO, CPO, COO, Product Manager/PM, Architect, Developer, QA, Security, DevOps, CMO/Marketing, Sales, Governance/Audit) — returns a persisted-data operating brief with objectives, project owners, task queues, blockers, pending approvals and active financial controls. CEO/CFO/COO briefs include company-wide campaign and customer-pipeline counts; Marketing reports campaigns and Sales reports lead/customer pipeline items. CEO/CFO/COO briefs are company-wide; other roles are scoped to their department. Lists are bounded for Telegram and point back to Supabase for the full queue.
- Engineering status includes a linked GitHub PR number and URL, merge state, and CI evidence recorded by Sutra. A GitHub Actions result appears as pending until the private poller persists its evidence to Supabase.
- `CEO, show my approvals.` — lists up to ten pending founder requests with the amount and outstanding department reviews; viewing the queue is audit logged and does not change approval state. Ready requests include private-chat Approve/Reject buttons backed by the same founder-only audited database RPC as the command form.
- `CEO, show standing code authority.` — shows the active grant for the exact Sutra GitHub repository and its fixed capabilities. `CEO, revoke standing code authority <authorization-id> because <reason>.` revokes it through a founder-only audited RPC. This grant covers task creation, branches, pull requests, merge, QA, Security and deployment; it cannot change a project budget, spending policy, or provider reservation.
- `CEO, set legal hold <project-id> because <reason>.` / `CEO, clear legal hold <project-id> because <reason>.` — writes an audited founder-only legal hold. A hold blocks the customer-email outbox; clearing one never restarts a paused project or closes a legal escalation.
- `CEO, run one bounded Kimi usage probe.` — queues one founder-audited Sutra-to-Hermes run, capped at a €0.10 reservation and still subject to the category monthly hard stop. Hermes may make up to three model iterations, which the database-priced reservation covers. It creates a dedicated diagnostic project/run, uses only the exact Kimi profile, retains unknown usage, and keeps Kimi disabled for normal roles.
- `retry PM review <run-id>` — a founder-only, audited retry for a failed PM stage after CEO, Product, CTO and CFO are complete and the project approval remains pending. Standard retries stay within three total attempts. After those are exhausted, the founder can authorize exactly one final recovery only for a terminal invalid-artifact-schema failure whose usage was reconciled. Every earlier reservation (including unknown usage) remains intact, and the final attempt requires a fresh reservation under the existing monthly hard stop. It never approves the project budget.
- `retry PM task <task-id>` — a founder-only, audited recovery for a blocked Product Manager planning task in a founder-approved project after a recognized artifact-validation failure. It preserves unknown reservations, permits at most three artifact runs total, and leaves all new inference subject to the existing spending policy and monthly hard stop. It does not approve further project spend.
- `retry Sales task <task-id> after artifact schema fix` — a founder-only, audited, one-time recovery for the same founder-approved Sales task after three terminal schema-validation attempts with all prior reservations reconciled. It requeues the task without creating a run, reservation, or expense; the next execution still uses the normal three-attempt limit and spend policy. It grants no project-spend, merge, or release authority.
- `retry CPO research <task-id>` — a founder-only, audited retry for the same blocked CPO market-research task after its terminal malformed-response failure. It keeps prior unknown usage reserved, allows at most three total artifact runs, uses the configured OpenAI GPT-6 Luna route, and leaves every new model call subject to normal spend preflight and the monthly hard stop. It grants no project spending, merge, or release authority.
- `retry agent review <run-id>` — a founder-only, audited retry for a recoverable failed CEO/CPO/CTO/CFO review stage when all prior stages succeeded. It uses only the same three-attempt ceiling, preserves unknown reservations, and still passes through the central spend reservation and monthly hard stop. PM retries keep their stricter CFO-complete gate.
- `retry GitHub dispatch <task-id>` — a founder-only, audited retry only for an exhausted GitHub permission-denied dispatch of the same approved Developer task. It resets one bounded three-attempt cycle, allows at most three founder retry cycles, and grants no spend, merge, or release authority.
- `retry Codex task <task-id>` — a founder-only, audited retry for the existing approved Developer task only after the metering database records zero provider requests and zero tokens. The prior unknown reservation is preserved and each retry uses a fresh database-priced reservation. Retries are bounded by the current founder-adjustable database limit of 1–3 total attempts per execution (default and hard maximum 3); changing that limit never starts a retry. The command grants no project spend, merge, or release authority.
- `defer QA and Security reviews for task <qa-task-id> because <reason>` — atomically defers the assigned QA task and its direct Security child in one founder-only, audited database transaction. Both remain incomplete with no review evidence; only their direct internal DevOps planning child is released. Spending, merge and release authority do not change.
- `restore review task <task-id> because <reason>` — restores a deferred QA or Security task to the ready queue after its prior workflow stage is complete. The review must still produce persisted evidence before later completion gates can pass.
- `Investigate an AI QA product. Initial budget maximum €500. Prepare a proposal.`
- `approve <approval-id> [comment]` or `reject <approval-id> [comment]`

Approval replies include IDs that can be used in the explicit approval command. There is no automatic external marketing, sales outreach, payment or production release.
